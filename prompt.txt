Build a production-quality Chromium browser extension called “DeepScope” — a lightweight, RAM-only, developer-focused web application discovery and universal fuzzy-search tool. The goal is to go far beyond ordinary DevTools search or basic network-capture extensions: when the user opens a website and starts a scan, DeepScope should discover and index as much browser-visible information as technically possible across the current page and, through an optional user-controlled Deep Scan, additional same-origin pages/routes and application states. It must discover and catalog HTML/DOM content, links, forms, scripts, JavaScript bundles and lazy-loaded chunks, CSS and CSS-referenced assets, source maps when available, manifests, iframes, module/import references, discovered URLs, SPA routes and route transitions, XHR/fetch requests, request/response metadata, API endpoints and JSON/text responses, and other browser-visible textual resources. The system should maintain a relationship/provenance graph so every finding clearly explains exactly where it came from, for example “Found: gpt6cb% → assets/asse099r9.js → route /models → discovered via dynamic import → line 18421”, or “Found: gpt_6_model → GET /api/models → JSON path models[4].name”. It must preserve the original text exactly as found while also supporting intelligent normalized and fuzzy matching, so a search for `gpt-6` can rank matches such as `gpt-6`, `gpt6`, `GPT-6`, `gpt_6`, `gpt-6x12`, `gpt6-preview`, `gpt6cb%`, and similar variants. Provide exact, substring, normalized, regex, and fuzzy search modes, with configurable search scopes for DOM/HTML, JavaScript, JS chunks, CSS, JSON, source maps, routes, URLs, request headers/bodies, response headers/bodies, iframes, and resource metadata. The search interface must show ranked results with match score, exact original string, resource type, URL/file, route/page, discovery method, initiator where available, line/column when available, and a surrounding context preview, with one-click navigation to the relevant resource/context in DevTools where the platform allows it.

Use Manifest V3, TypeScript, native Chromium Extension APIs, a DevTools panel as the primary interface, content scripts for page/DOM/route discovery, a minimal service worker for coordination, and Web Workers for heavy parsing/indexing so the UI remains responsive. Use `chrome.devtools.network` for DevTools network/resource information, `chrome.webRequest` where appropriate and permitted for broader request observation, `chrome.webNavigation` for navigation/frame/route tracking, `chrome.scripting` and content scripts for DOM/runtime discovery, and an optional, explicitly user-enabled `chrome.debugger`/CDP-powered Deep Capture mode only where deeper instrumentation is needed. Do not use React, Redux, Next.js, Express, Electron, Playwright, Puppeteer, a backend, a cloud service, or any large framework. Keep the dependency footprint extremely small: prefer native browser APIs; use only lightweight libraries when they materially improve capability, such as `uFuzzy` for fast fuzzy ranking and optionally `source-map`, `acorn`, and `acorn-walk` for deeper source-map/JavaScript analysis. Bundle all dependencies locally; never load runtime libraries from CDNs.

The extension must be completely session-based and must not persist captured website data to disk, IndexedDB, localStorage, a database, server, telemetry endpoint, or cloud service. All captured content and search indexes should exist only in RAM for the active DevTools/scan session and be destroyed when the session ends. However, do not interpret “RAM-only” as “do not store anything”: the system must intentionally retain enough captured content in memory to make repeated searching instant. Optimize memory aggressively by avoiding duplicate raw/normalized/indexed copies, using compact records and token-to-resource indexes, deduplicating identical resources by URL/content hash, processing large resources in streaming or chunked fashion where practical, and moving expensive parsing/indexing into Web Workers. Add configurable memory budgets and live memory accounting in the UI, for example current estimated RAM usage, percentage of configured budget used, indexed text size, raw-content size, resource count, route count, request count, chunk count, and index size. Provide controls such as 128 MB / 256 MB / 512 MB / 1 GB session budgets, maximum individual response size, maximum indexed text size, maximum resource count, whether to retain raw responses, whether to analyze source maps, and whether to include binary assets. Never unnecessarily copy large binary files into the index; by default catalog binary/media/font resources using metadata only, with optional on-demand inspection if technically possible. When approaching the memory budget, clearly warn the user and allow configurable behavior such as stop capture, discard oldest raw bodies while preserving compact metadata/index entries, or stop deep analysis. Make memory usage visible at all times and design algorithms to remain efficient on extremely asset-heavy sites.

Create two operating modes. Passive mode should be extremely lightweight and primarily observe resources, navigation, DOM changes, routes, and network activity that naturally occur while the user browses. Deep Scan mode should be user-triggered and should systematically explore the browser-visible surface of the current web application: recursively process discovered same-origin links/routes, SPA route transitions, script references, lazy resources, module imports, source-map references, API URLs, embedded frames where permitted, manifests, CSS imports and asset references, and other discoverable application paths. Provide configurable controls for scan depth, same-origin vs selected subdomains, third-party resource inclusion, route exploration, resource recursion depth, source-map analysis, iframe scanning, lazy-loading observation, API response capture, SPA transition monitoring, and per-page/resource/request limits. Never perform uncontrolled internet-wide crawling; keep discovery bounded to the user-selected site/origin and clearly display the current scope. Maintain a temporary discovery graph showing pages/routes, resources, chunks, endpoints, and the relationships between them, including exactly how each item was discovered: DOM link, router, history API, JS string, dynamic import, CSS reference, network request, sitemap, manifest, iframe, etc.

The UI should be exceptionally information-dense but clean and lightweight, designed for developers and built with plain HTML/CSS/TypeScript. Use a DevTools panel with sections such as Overview, Search, Routes, Resources, Network, Discovery Graph, and Settings/Controls. The Overview should show live counters such as pages/routes discovered, resources, JS bundles/chunks, APIs, requests, responses, source maps, frames, indexed strings, and RAM usage. The Search screen should provide one universal search box, search mode selector, scope filters, result ranking, context snippets, and provenance. The Routes screen should show a hierarchical route tree and discovery method. The Resources screen should show URL, type, status, size, route, initiator, discovery method, source-map availability, and indexed status. The Network screen should show request/response metadata and captured textual bodies according to current permissions/settings. The Discovery Graph should visualize relationships such as route → chunk → API endpoint → response. The Controls panel should expose every major behavior without hiding important functionality behind fixed assumptions. Include pause/resume, clear current session, recapture/reload, Deep Scan start/stop, reindex, memory cleanup, export only when explicitly requested by the user, and per-category toggles.

Optimize the search/indexing system heavily. Use a staged pipeline: fast exact/substring candidate lookup first, normalized matching second, fuzzy ranking only on the reduced candidate set, and regex as a separate explicit mode. Normalize separators and case intelligently while preserving the original string and exact location. Extract useful searchable units from large JavaScript/CSS/HTML/JSON resources instead of repeatedly fuzzy-searching entire megabyte-scale files. For JavaScript, detect URLs, route-like strings, identifiers, object keys, string literals, dynamic import targets, fetch/XHR targets, and sourceMappingURL references without requiring a heavyweight full compiler pipeline by default. Enable deeper AST parsing only when the user turns on advanced JS analysis. For source maps, when available, map minified resource locations to original sources and display both original and compiled provenance. Deduplicate repeated API responses and static assets. Avoid reprocessing unchanged resources. Use incremental indexing so newly captured content becomes searchable quickly without rebuilding the entire index.

Build for Chromium browsers such as Chrome and Edge, document all required permissions, minimize permissions, and make sensitive capabilities opt-in. Do not collect or transmit user browsing data externally. Keep all processing local. Include strong error handling for large resources, unsupported content types, malformed JavaScript/JSON/CSS, cross-origin restrictions, service-worker suspension, closed DevTools, navigation races, duplicate requests, and sites with heavy SPA activity. Ensure the extension gracefully reports limitations instead of pretending it can access server-side code or resources that the browser never received. Add diagnostics explaining why a resource could not be captured or analyzed. Include a clear README covering architecture, permissions, privacy model, build commands, development mode installation, and limitations.

The final result should feel like a “beast” of a discovery tool while remaining technically lightweight: one extension, no backend, no database, no persistent capture storage, minimal dependencies, bounded RAM, worker-based processing, aggressive deduplication, on-demand deep analysis, comprehensive provenance, route/resource/network discovery, and a single powerful fuzzy search that lets a developer search the entire browser-observable surface of a web application and immediately understand exactly where every result was found. Prioritize performance, correctness, explainability, user control, and minimal resource usage over adding unnecessary frameworks or cosmetic complexity.
